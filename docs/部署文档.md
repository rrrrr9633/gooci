你在一台客户 VPC 云服务器上工作。当前目录同级有四个项目：

- gooci              主工作台（Spring Boot 控制台 + 网关，浏览器只打它）
- Big-Data-Modle     设备预测性维护（外接模块 1）
- cad-transform      CAD 拆解（外接模块 2）
- weekly_plan_web    周计划（外接模块 3）

目标：把 1、2、3 在本机启动成旁挂进程，并接入 gooci 的外接模块壳。不要把它们并进 gooci 主后端。不要改客户可见域名/路径模型。

==================================================
硬约束（违反即做错）
==================================================

1. 客户浏览器永远只打 gooci 的公网入口（一个域名 / 一条 A 记录）。
   正确跳转：
     工业 APP 砖块
       → /workbench/ext/{appCode}
       → 同域 /ext/{appCode}/**
       → gooci 网关转到 TM_APP_OPEN.TARGET_URL
   禁止：浏览器直开 5174/8777/8000 等模块端口。
   禁止：为模块再写第二条公网 A 记录、再买域名、再给模块机公网 IP。
   禁止：把公网 IP（例如 154.201.65.68）或公网域名写进 TARGET_URL。

2. TARGET_URL 只填本机环回或本 VPC 私网。
   四个项目若在同一台机：http://127.0.0.1:<模块端口>
   模块进程只监听 127.0.0.1（或内网网卡）。不要 0.0.0.0 对公网暴露。

3. 模块自己不上报、不回调、不改 gooci 内核表。
   控制台知道新模块的唯一方式：厂商调植入接口写 TM_APP_OPEN。
   接口：POST /api/ops/apps/implant
   鉴权：厂商 JWT（先 POST /api/ops/auth/login）。
   已存在则更新名称/入口/目标，不要重复插脏行。

4. 网关改写规则（模块白屏的常见原因）：
   - 只改 HTML 的 src/href、CSS url()、以及 /assets/ /src/ 这类静态根
   - 禁止改 JS 字符串里的 '/'、路由 path、fetch('/api/...') 字面量
   - 不要二次改写 importmap
   - 不要打乱 Vite <base>
   生产不要用 Vite dev 当 TARGET_URL（/@vite、/src 从站点根加载会白屏）。
   必须：build 后的静态产物 + 其 API 进程。

5. 探活是 gooci JVM 去 TCP 连 TARGET_URL，不是浏览器、不是 DNS。
   可达 = 本机听端口；未达 = 没起/端口错/只绑了别的网卡。

6. 不要抄 iSESOL 子域名、不要出现「设备云眼」「应用管家」。
   种子里若有 EXT_PACK_AI / DEVICE_EYE / APP_STEWARD / DEMO_SHELL 且本机没有对应进程：隐藏或 retire，不要当已开通砖块。

7. 不改 gooci 登录/权限协议。模块私有表只属于模块自己的库。
   旁挂接入时不要重启 gooci 主进程（能热挂就热挂）。

建议编码（写入 TM_APP_OPEN，不要再往 Java 里写死端口）
==================================================

| 目录              | appCode     | appName         | entryPath                    | TARGET_URL 形态              |
|-------------------|-------------|-----------------|------------------------------|------------------------------|
| Big-Data-Modle    | EXT_PDM     | 设备故障预测    | /workbench/ext/EXT_PDM       | http://127.0.0.1:<画面端口>  |

若预测性维护是「前端端口 + 独立 API 端口」：TARGET_URL 填【浏览器画面】那个 origin，不是 API 端口。
API 仍只给该模块自己用，或由该模块前端相对路径访问；经网关时接口也必须落在 /ext/EXT_PDM 之下，不能让浏览器打第二个 origin。

【阶段 0 · 摸清现场】
- 列出四份目录的绝对路径、技术栈、现有启动脚本、当前是否已有进程、监听地址和端口。
- 读 gooci 的 application*.yml / .env：库、JWT、已有 gooci.ext-*-url、默认 profile。
- 确认 gooci 已在跑（或按仓库生产档拉起），只绑需要的端口。
- 输出一张表：项目、进程、listen、健康检查命令。未探明前不要改代码。

检查点 0：四项目启动方式已写清；gooci 能本机 curl 通 /api/site/meta。

【阶段 1 · 按生产产物启动三个模块】
对每个模块：
1. 优先生产启动（Java jar / Python 已有 server / nginx 或静态 + API），禁止长期用 npm run dev。
2. 前端若是 Vite：npm run build，再用预览/静态服务托管 dist，host=127.0.0.1，固定端口。
3. 若模块自带 API：同样只听 127.0.0.1，并保证画面里的接口是相对路径或同 origin，不要写死公网 IP。
4. 端口冲突就改模块自己的配置，不要改 gooci 的 8080（或它现用的网关端口）。
5. 用 systemd 或明确的 nohup/日志文件保活，写清重启命令。
6. 本机验证：curl -I http://127.0.0.1:<端口>/  要 200/302，且从公网 IP:该端口 应拒绝或根本没监听。

检查点 1：三台模块本机可打开画面 HTTP；ss/lsof 显示 127.0.0.1:端口；公网扫不到模块端口。

【阶段 2 · 植入，不要改网关协议】
1. 用厂商账号登录（种子默认 ops / GooCi@2026，若现场已改则用现场账号）。
   POST /api/ops/auth/login
2. 查企业列表 GET 运营企业接口，记下演示/目标企业 enterId。
3. 对三个模块分别 POST /api/ops/apps/implant
   JSON：
   {
     "enterId": "<企业id>",
     "appCode": "EXT_PDM|EXT_CAD|EXT_WEEK",
     "appName": "<中文名>",
     "entryPath": "/workbench/ext/<appCode>",
     "targetUrl": "http://127.0.0.1:<该模块画面端口>"
   }
4. 不要把端口写回 KernelDataSeed / application.yml，除非只是本机开发默认值。
   云上以 TM_APP_OPEN 为准。
5. 用运营台或 GET 企业模块列表看 health：up / down / none。
   down 先修监听，再改 targetUrl，不要先改网关改写逻辑。

检查点 2：三行 TM_APP_OPEN 有入口路径、TARGET_URL 为 127.0.0.1、探活为 up。

【阶段 3 · 同域壳验收】
1. 企业账号登录 gooci 工作台（种子演示 admin / GooCi@2026，现场以实际为准）。
2. 工业 APP 页出现三块砖，点进去 URL 仍是 /workbench/ext/EXT_* ，iframe 源是同域 /ext/EXT_*/。
3. 本机模拟网关：
   curl -sI http://127.0.0.1:<gooci端口>/ext/EXT_PDM/
   curl -sI http://127.0.0.1:<gooci端口>/ext/EXT_CAD/
   curl -sI http://127.0.0.1:<gooci端口>/ext/EXT_WEEK/
   应是 200 且内容来自模块，不是内置空壳。
4. 若白屏：先看 iframe 里 JS 是否还在请求站点根 /src、/@vite、/assets（说明用了 Vite dev 或改写过猛）。
   修模块 base/publicPath 或改成 build 产物，不要扩大 JS 全文改写。
5. 模块内点击、接口、静态资源都必须继续走 /ext/{appCode}/... 。

检查点 3：三块砖可进、无白屏、浏览器开发者工具 Network 里没有模块私有端口、没有第二公网主机。
